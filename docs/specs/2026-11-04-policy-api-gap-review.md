# 모아북 정책서 · API · 현재 구현 대조

검토일: 2026-11-04. 앱 구현은 변경하지 않았으며, 이 문서는 수정 범위와 연동 전 확인 사항을 기록한다.

후속 확인: [백엔드 재확인 결과](2026-11-04-backend-verification.md)에 API 문서·서버 main 코드 대조, 삭제 폴더 다섯 항목의 대체 방안, 남은 저장 계약을 기록했다. 아래는 최초 문서 대조 결과이며, 추가 판정은 후속 문서를 함께 참조한다.

**사용자 확정 변경:** 현재 상태는 기록 날짜와 무관하게 마지막으로 추가한 상태 기록을 따른다. 아래의 날짜 우선 상태 계산·과거 기록 추가 후 상태 유지 내용은 원본 정책의 검토 이력이며 새 구현 기준에서 제외한다. 최신 실행 기준은 작업계획서와 HTML을 따른다. 띠지 이유 선택과 기록 목록의 날짜 정렬 규칙은 이번 합의로 변경하지 않았다.

- [정책서](https://claude.ai/artifact/CGrhmuG8FsCce51VeHxWUy): 2026-10-20 초안 2차. Safari에 열린 원문 전체와 부록을 확인했다. 정책 확인용 화면 33개를 설명한다.

- `lib/design_preview/`: A/C 시안, 로컬 상태와 샘플 데이터로 동작한다.
- `lib/main.dart`, `lib/app/router/`, `lib/features/`, `lib/data/`: 현재 본앱 진입점과 기존 API 연동 코드.
- 공유 저장 진입점 `lib/features/share_import/`와 `ios/MoabookShareExtension/MoabookApi.swift`도 확인했다.
- 저장소의 10월 9일 백엔드 요청 초안은 최신 정책과 다르다. 특히 기존 책 체크 선택, 쉬는 상태, 완독 시작일, 기록 종류별 입력은 이번 정책을 우선해야 한다.

## 판단

새 UI의 기본 구조는 있으나, 정책서 이후 바뀐 화면과 데이터 동작은 상당 부분 미반영이다. 또한 디자인 프리뷰는 본앱 라우터에 연결되어 있지 않아, 프리뷰 수정만으로 운영 앱이 바뀌지는 않는다.

작업을 세 갈래로 나누는 것이 적절하다.

1. 정책이 명확한 프리뷰 UI 및 입력 동작 수정.
2. 기존 API 호출·모델 교체와 컬렉션·독서 기록 데이터 계층 추가, 본앱 연결.
3. 저장·중복·상태 계산처럼 문서만으로 구현을 확정할 수 없는 서버 계약 확인.

현재 프리뷰 화면 레지스트리는 28개다. 정책서와 화면을 세는 방식이 달라 숫자만으로 누락 개수를 판단하면 안 된다. 별도 추가가 명확한 화면은 **신규 빈 컬렉션, 컬렉션 중복 안내, TODO 이유 기록 입력**이다.

재사용할 수 있는 구조도 있다. 기본 서가 3단과 가변 권수 페이지, 세로 제목, 좌우 페이지 이동, 카드 탭·스와이프 전환, 기본/주제 탭과 컬렉션 목록 진입, 이유 없는 책의 띠지 숨김은 이미 있다. 촬영·OCR·갤러리는 본앱에 실제 구현이 있으므로 새 화면에서 기존 기능을 연결할 수 있다.

## API 대조와 본앱 영향

| API | 현재 구현과 차이 | 대응 |
| --- | --- | --- |
| `GET /mybooks/store` | 새 문서는 모든 내 책과 `keyword/page/limit` 설명. 현재는 기존 TODO 서점으로 해석하고 `size`, `sort` 전송 | 통합 서가로 의미 변경. 문서의 `limit`과 예제 이름의 `size` 충돌 확인 후 요청 통일 |
| 기존 내 책 검색 | `searchMyBooks()`는 `GET /mybooks?query=...` | 새 `/mybooks/store?keyword=...` 계약으로 교체 |
| `POST /mybooks` | 새 요청에서 `historyInfo`, ISBN·소개·출간일 제거. 현재 검색 저장·공유 저장은 옛 필드를 사용 | 요청 모델 교체. 최초 기록 생성 방식은 아래 선결 확인 사항 참고 |
| `GET /mybooks/{id}` | 새 앞면 응답은 제목 등 최상위 필드. 현재 파서는 `bookInfo/historyInfo` 중첩을 기대 | 현재 코드에 새 응답을 넣으면 제목·저자 등이 빈 값으로 나옴. 전용 응답 모델과 `totalRecords` 추가 |
| `GET /mybooks/{id}/records` | 신규, 현재 datasource·모델·provider 없음 | 타임라인 조회 추가. 문서 표는 `records` 필드지만 예제는 최상위 배열이므로 확정 필요 |
| `POST /mybooks/{id}/records` | 신규. `recordType`, UTC `recordDate`, 선택 `memo`; FREE 필수, 최대 400자. 응답 `recordId` | 입력 검증과 중복 탭 방지, 저장 후 앞·뒷면 재조회 |
| 기록 단건 GET / DELETE | 문서에는 있으나 정책은 삭제 UI를 포함하지 않음 | API 존재만으로 삭제 UI를 추가하지 않음 |
| `GET /collections`, `GET /collections/{id}`, `POST /collections`, `PUT /collections/{id}` | 본앱에 컬렉션 datasource·모델·provider·화면 연결 없음 | 대표 책 0~2권, 9슬롯 상세, 생성, 전체 교체 저장 구현 |
| 컬렉션 PUT | 책 ID와 `slotNo`로 최종 목록 전체 교체, 빠진 책은 컬렉션에서만 제거 | 변경하지 않은 슬롯도 보존해서 전송. 한 권 추가 요청으로 오해하면 기존 책이 빠짐 |
| 문서의 삭제 폴더 | 직접 책 추가, 독서 시작 PATCH, 책 수정 PATCH, 히스토리 조회가 이동되어 있음 | 신규 앱에서 계속 유효하다고 전제하지 않음. `getHistoryBooks`, `updateReadingStatus`, `updateMyBook`, 수동 추가 경로 재검토 |

핵심 변경 파일:

- `lib/data/datasource/mybook_datasource.dart`: 요청 경로·페이지 인자·저장 결과·앞면 파서 교체, 기록 API 추가.
- `lib/domain/model/my_book_detail.dart`, `store_book.dart`, `book_item.dart`: 새 응답과 페이지 수·기록 개수·요청 모델 반영.
- `lib/features/home/provider/home_provider.dart`: 통합 서가로 변경. 기존 독서 시작 PATCH 대신 기록 생성 흐름.
- `lib/features/book_search/provider/book_search_provider.dart`: 옛 `historyInfo` 저장 제거, 생성 결과·중복 결과에 책 ID 유지.
- `lib/features/book_info/provider/book_info_provider.dart`: 옛 PATCH 편집 구조를 새 독서카드와 기록 상태로 교체.
- `lib/app/router/app_router.dart`: 기존 home/history 중심 경로에서 새 서가·컬렉션·독서카드 화면으로 연결.
- `lib/features/share_import/provider/share_import_provider.dart`, `ios/MoabookShareExtension/MoabookApi.swift`: 새 저장 요청과 최초 기록 계약 반영. iOS 확장은 Dart와 별도로 수정 필요.
- `lib/widget_bridge/`: 홈 데이터의 의미가 전체 책으로 바뀔 때 기존 위젯의 대상 책·동작도 함께 점검.

앱 기본 API 주소는 `https://moabook.shop`, Postman 요청 주소는 `https://api.ikdaman.shop`이다. 개발·운영 주소 관계를 확인하고 환경별로 설정해야 하며, 문서 주소만 보고 운영 주소를 일괄 변경하면 안 된다.

Postman의 추가 모순도 정리해야 한다: 대표 책/슬롯 설명에는 `myBookId`지만 예제는 `mybookId`, 표지는 필수 설명이지만 예제는 null, PUT의 슬롯 번호는 설명상 생략 가능하지만 표에는 필수, 수정 응답 예제의 `createdAt`이 생성 때와 다르다. 오류 예제 일부는 이름이 403인데 HTTP 코드가 200으로 등록돼 있다. 클라이언트는 최종 계약을 기준으로 만들고 명세 오류를 조용히 정상 데이터로 처리하지 않아야 한다.

## 권장 작업 순서와 완료 기준

1. 프리뷰에 정책 반영: 슬롯 9칸·빈 컬렉션·중복 안내·컬렉션 담기 목적 전달, 입력 및 문구 정리. 검토 후 사용자 지정에 따라 마지막 정책서 스크린샷의 밝은 테마를 구현 기준으로 삼는다.
2. P0 계약 확정 후 datasource와 도메인 모델 구현. 서버 변경 전에는 운영용 기존 호출을 무작정 제거하지 않는다.
3. 통합 서가 → 검색/촬영/갤러리 → 최초 저장 → 독서카드 → 기록 추가까지 본앱 연결.
4. 컬렉션 생성 → 빈 칸에서 검색 → 기존/신규 책 연결 → 중복 안내 → 슬롯 유지 제거 연결.
5. 공유 확장·위젯·기존 데이터 호환, 이미지 저장, 실패 복구를 확인.

검증 시 반드시 포함할 사용자 시나리오:

- 읽고 싶은/읽는 중/읽은 책 저장 각각 기록이 정확히 1개이며 선택 날짜를 유지.
- 과거 상태 기록을 나중에 추가해도 최신 상태 유지. 같은 날짜는 나중 생성 기록 우선.
- 새 TODO 기록으로 띠지가 갱신되고, 이후 완독 기록을 추가해도 띠지는 유지.
- 컬렉션 2번 슬롯 제거 후 3번 책이 이동하지 않음. 신규 책은 첫 빈 칸에 들어감.
- 같은 컬렉션 중복 차단, 다른 컬렉션에는 같은 책 담기 가능, 9권 초과 차단.
- 신규 책 저장 성공 후 컬렉션 연결 실패 시 재시도해도 서가 책/기록이 중복되지 않음.
- FREE 공백 저장 차단, TODO 이유 400자, 문장·페이지 추가 입력 없음, 날짜와 완료 화면 일치.
- 빈 컬렉션·표지 없음·메타 정보 없음·통신 실패·소유권 오류 처리.
